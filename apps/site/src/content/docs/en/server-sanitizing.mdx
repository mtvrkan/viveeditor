The editor only produces a known set of HTML, but anyone can post any HTML to your server. Clean it there before you store or show it. `@viveeditor/sanitize` for Node and `viveeditor/sanitizer` for PHP 8.4+ keep exactly what the editor produces and remove everything else. They share one allowlist and one test corpus and give the same output.

## Install

For Node.js 22.12 or newer:

```sh
npm install @viveeditor/sanitize
```

For PHP 8.4 or newer, with the `dom` and `mbstring` extensions and no other dependencies:

```sh
composer require viveeditor/sanitizer
```

On Laravel, use [viveeditor/laravel](/en/docs/laravel/), which brings the PHP sanitizer with it.

## Clean the HTML

```ts
import { sanitizeHtml } from '@viveeditor/sanitize'

const clean = sanitizeHtml(request.body.html, { embeds: true })
```

```php
use Viveeditor\Sanitizer\Sanitizer;

$clean = Sanitizer::sanitize($html, ['embeds' => true]);
```

Every element and attribute is rebuilt with a full HTML5 parser (`parse5` in Node, `Dom\HTMLDocument` in PHP), so the output reads the same way in every browser. Cleaning twice gives the same result.

## Options

| Option | Default | Effect |
| --- | --- | --- |
| `embeds` | `false` | Keeps video and audio embeds. Players are rebuilt from the provider and id, never copied. |
| `allowBase64` | `false` | Allows images stored as `data:` addresses (PNG, JPEG, GIF, WebP, AVIF). |
| `allowRelativeImages` | `false` | Allows relative image addresses. |
| `fontFamilies` | 8 common families | Replaces the list of font families that may appear on `span`. Each entry is a comma-separated family list of plain names, such as `Inter, sans-serif` or `'Fira Code', monospace`; an entry with anything else throws an error when the sanitizer starts. The default is `serif`, `sans-serif`, `monospace`, `Arial, Helvetica, sans-serif`, `Georgia, serif`, `'Times New Roman', Times, serif`, `'Courier New', Courier, monospace` and `Verdana, Geneva, sans-serif`. Pass the same list you give the editor. |
| `maxBytes` | 2 MB | HTML larger than this throws `TOO_LARGE`. |
| `maxTags` | 100 000 | HTML with more opening tags than this throws `TOO_COMPLEX`. 2 MB of normal content has about 20 000 to 40 000. |

Turn `allowRelativeImages` on only if you need it: a relative image address makes every reader's browser send a GET request to your own site, which a writer could aim at an address that changes something.

## Errors

The sanitizer never cuts HTML short. When it cannot clean the input, it throws:

| Code | When |
| --- | --- |
| `TOO_LARGE` | The HTML is larger than `maxBytes`. |
| `TOO_COMPLEX` | The structure would make the parser slow or memory hungry: more than `maxTags` opening tags, more than 64 attributes on one tag, nesting deeper than 512 levels, far more elements than the input has tags, or a `<template>` tag. The editor never writes such HTML. |

In Node the error is a `SanitizeError` with a `code`:

```ts
import { SanitizeError, sanitizeHtml } from '@viveeditor/sanitize'

export function cleanArticle(html: string): string | null {
  try {
    return sanitizeHtml(html)
  } catch (error) {
    if (error instanceof SanitizeError) return null
    throw error
  }
}
```

In PHP it is a `SanitizeException` whose `reason` is `SanitizeException::TOO_LARGE` or `SanitizeException::TOO_COMPLEX`:

```php
use Viveeditor\Sanitizer\SanitizeException;
use Viveeditor\Sanitizer\Sanitizer;

try {
    $clean = Sanitizer::sanitize($html);
} catch (SanitizeException $error) {
    $clean = null;
    $reason = $error->reason;
}
```

## What is kept

- **Links** keep `http`, `https`, `mailto`, `tel` and relative addresses, and always get `rel="noopener noreferrer nofollow"`.
- **Images** need `https` addresses. `allowBase64` and `allowRelativeImages` widen that.
- **Embeds** are removed unless you pass `embeds: true`.
- **Figures** keep `figure` and `figcaption`; `data-align` survives only as `left`, `center` or `right`.
- **Tables** keep `data-width="full"`, `data-align="center"`, `data-border` (`rows` or `none`) and `data-striped="true"`. A full-width table drops its fixed width.
- **Numbered lists** keep `start` and a `type` of `a`, `A`, `i` or `I`.
- **`style`** keeps only text alignment, paragraph indent (2 em steps up to 16 em, on paragraphs and headings), line height (1, 1.15, 1.5 or 2, on paragraphs and headings), font sizes on `span` (the editor's steps, or 6 to 96 pt in half points), font families from the `fontFamilies` list, text and highlight colour, table widths and border colour, the bullet style of a list (disc, circle or square), and the background colour, horizontal alignment and vertical alignment (middle or bottom) of table cells. A font size inside another font size, and superscript or subscript inside another, are dropped so nesting cannot blow text up or hide it.
- **`id`, `name`, `form` and event handlers** never pass.
- **Scripts, styles, frames, SVG and similar elements** are removed together with their content.
- **Mentions, formulas and footnotes** are kept in exactly the form the editor writes them. A mention id or formula that fails its check, or one placed inside a link or a footnote, is reduced to its text. Footnotes keep only bold, italic and links. A footnote placed inside a link is reduced to its text.

## PHP memory note

In PHP the parser cannot be stopped from inside, so the PHP sanitizer checks the structure before it parses. Hostile inputs, such as short runs of unclosed formatting tags or very deep nesting, are refused with `TOO_COMPLEX` in well under a second and without building the document.

What passes the check is limited by `maxBytes` and `maxTags`. In our measurements a document with 100 000 elements used about 70 MB, and 2 MB of broken markup that creates no elements used up to about 130 MB, because the parser records every error it meets. Give the endpoints that sanitize a `memory_limit` of 256 MB, or lower `maxBytes` and `maxTags`: half the limits need about half the memory.

Very long HTML with misnested formatting tags, which older systems sometimes write, can be refused in PHP sooner than in Node, because PHP must decide before it parses. The editor never writes such HTML.

## When to clean

<Steps>
1. **On save.** Clean the posted HTML before you store it.
2. **On print.** Show stored HTML through a cleaning helper too (`@viveHtml` in Laravel). Rows written before you added cleaning, or written outside your forms, then stay safe.
</Steps>

<Callout type="warn" title="Never print raw HTML">
Do not print stored HTML unescaped without cleaning it, even if it was cleaned once on save.
</Callout>
